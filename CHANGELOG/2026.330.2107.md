# 2026.330.2107 — docs(pixi): pin 0.84.2's lock/platform pairing rule and the preferred lockfile path

## Summary

The `pixi` skill taught the pre-0.84.2 shape and a cache variable pixi never creates. This corrects it
with the measurements from the pixi 0.84.2 upgrade and the openwebui build that the upgrade broke.

- **`RATTLER_CACHE_DIR` retained as a row, annotated `not set`** (the skill no longer presents it as a
  cache root to configure). Measured on 0.70.2 **and** 0.84.2: a `--frozen` install never creates it;
  the package cache is `PIXI_CACHE_DIR` (`pkgs/`, `uv-cache/`), and `--frozen` fetches **no repodata**.
- **The `--frozen` platform rule, which is the real upgrade hazard.** `[system-requirements]
  libc = 2.39` changes the resolved platform to `linux-64-glibc-2-39`, so a lock resolved for a bare
  `linux-64` fails:

  ```
  Error: the lock file has no entry for platform 'linux-64-glibc-2-39' in environment 'default'
  help: Run `pixi lock` to resolve it for this platform.
  ```

  The section is **deprecated** in 0.84.2 and **not required once the builder stops injecting it** —
  measured: a bare `linux-64` manifest locks and installs `--frozen` cleanly. While the injection is
  compiled in (today), a candy declares the section and locks for `linux-64-glibc-2-39`; never declare
  it and keep a bare-platform lock.
- **The regenerate example is rewritten** to the measured form (`pixi lock` with the same 0.84.2 the
  builder installs, then check the lock's platform name), replacing the old shell one-liner that
  appended the section and then locked.
- **The lockfile + `--frozen` is stated as the PREFERRED path**, with the solve fallback kept and
  labelled as supported-but-not-preferred (the builder keeps both install commands).
- **A step-by-step lock-update procedure** is added: match the builder's pinned pixi, pick the platform
  the candy declares (bare `linux-64` vs `linux-64-glibc-2-39` — never mix), regenerate with a scratch
  `PIXI_HOME`, verify the platform line and `install --frozen`, and commit `pixi.toml` with `pixi.lock`.

```
$ pixi --version
pixi 0.70.2
$ ls -A /tmp/f0702c

```

The build-stage cache mount, measured with a controlled BuildKit build using the stage's exact flags
(`--mount=type=cache,dst=/tmp/pixi-cache,uid=1000,gid=1000`, `PIXI_CACHE_DIR` set):

```
build 1 (writer): pixi install; ls -A /tmp/pixi-cache → pkgs  repodata  uv-cache
build 2 (reader, fresh layer, same mount): ls -A /tmp/pixi-cache → pkgs  repodata  uv-cache  SIZE=4.4M
```

A newly downloaded package lands in `pkgs/` and the next build re-reads it. The daemon prunes that
cache by its own policy, so the skill states no fixed directory or byte count.

### Spike

| Candidate | Run + result |
|---|---|
| A — bare manifest, no section | `pixi lock` → `- name: linux-64`; `pixi install --frozen` → `✔`, exit 0 |
| B — manifest with `[system-requirements] libc = 2.39` | `pixi lock` → `- name: linux-64-glibc-2-39`; `pixi install --frozen` → `✔`, exit 0 |
| C — the mismatch the rule forbids: a bare lock, the section appended before install | `pixi install --frozen` → `Error: the lock file has no entry for platform 'linux-64-glibc-2-39'`, exit 1 |

A and B are both valid **pairings** of manifest and lock; C is the pairing that fails. That is the
rule the skill states.
